# 技術仕様書 (Architecture Design Document)

このドキュメントは、`docs/product-requirements.md`(PRD)と `docs/functional-design.md`(機能設計書)を実現するための技術構成を定める。機能設計書で「`architecture.md` で定める」とした項目(ビルドツール、データベースの読み書きの権限、通信量の見積もり、E2Eテストのツールなど)も、ここで決める。

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン | 選定理由 |
|------|-----------|----------|
| TypeScript | 5.9.x | 状態・行動・データの形を型で表し、ルールの実装ミスをコンパイル時に見つける。プロジェクトの方針(CLAUDE.md)で5.xとしている。7.x(Go実装)は、typescript-eslint が対応していない(`<6.1.0`)ため採用しない |
| Node.js | v24 LTS(devcontainerは `lts` を指定。パッチ番号は固定しない) | 開発時のビルド・テスト・スクリプトにだけ使う。遊ぶときには使わない |

| Java(JDK) | 11以上 | Firebase Emulator Suite の Realtime Database エミュレータが Java で動くため(開発時とCIだけ)。devcontainer に入れる |
| 実行環境(遊ぶとき) | ブラウザ | PRDの対応環境: PCの最新版 Chrome / Edge / Firefox / Safari、スマホの iOS Safari・Android Chrome の最新版 |

### フレームワーク・ライブラリ

実行時に読み込むライブラリは、**Firebase の Web SDK だけ**にする。

| 技術 | 用途 | 選定理由 |
|------|------|----------|
| firebase(モジュール形式。`firebase/app`・`firebase/auth`・`firebase/database` だけを読み込む) | 匿名認証と Realtime Database への接続 | サーバーのプログラムを書かずに、全員で1つの数字を共有できる。必要な部分だけを読み込めるので(不要なコードは、ビルドで取り除かれる)、配信サイズを抑えられる。バージョンは12.x系の、実装時点の最新の安定版に固定する |
| DOM API + SVG | 画面・小人・グラフの描画 | 要素は数百個で、フレームワークの状態管理がなくても十分扱える。SVGは拡大してもくっきりし、CSS変数で色を切り替えられる。依存を増やさず、読み込みも軽くなる |
| CSS(CSS変数・メディアクエリ・キーフレームアニメーション) | レイアウト、配色、動き | 跳ねる・降りてくる・点滅するなどの動きを、CSSだけで作れる。`prefers-reduced-motion` への対応も、CSSだけで行える |

### 却下した案

| 案 | 却下の理由 |
|----|-----------|
| Cloud Firestore | 1つの数字を、大勢が高速に書き換える用途に向かない(同じデータへの書き込みの頻度に制限がある)。Realtime Database は、サーバー側で加算する命令(`increment`)で、同時に押しても取りこぼさない |
| Firebase の REST API + イベントの購読(自前で組む) | SDK より小さくできるが、再接続、条件付きの書き込み(トランザクション)、切断時の自動処理(`onDisconnect`)を、自分で作ることになる |
| 自前のサーバー(WebSocketなど) | サーバーの用意・管理・費用が必要になる。このゲームには、Realtime Database で足りる |
| Cloud Functions(サーバー側の関数) | 有料のBlazeプランが必要。不正対策(P2)で、必要になったら導入する |
| React などのフレームワーク | 画面の要素が少なく、状態は、ドメイン層が組み立てた `RoundView` を、描画するだけ。依存を増やすほどの利点がない |

## アーキテクチャパターン

### レイヤードアーキテクチャ(4層)

機能設計書の構成を、次の依存方向で実装する。

```
┌──────────────────────────────┐
│   UI層 (src/ui)               │ ← 画面・小人・グラフ・演出の描画、入力の受付
├──────────────────────────────┤
│   アプリケーション層 (src/app)  │ ← 画面の流れ、部屋への参加、連打のまとめ送り、AI担当
├──────────────────────────────┤
│   ドメイン層 (src/domain)       │ ← 時計、目標、判定、ポイント、結果の一覧、AIの手の選択
├──────────────────────────────┤
│   インフラ層 (src/infra)        │ ← Firebaseの読み書き、時計の同期、ブラウザに覚える設定
└──────────────────────────────┘
```

依存は、次のとおりにする。

```
UI → アプリケーション → ドメイン           (OK)
アプリケーション → インフラの「インターフェース」 (OK。実装には依存しない)
インフラ(実装) → ドメインの型               (OK)
UI → ドメイン(型と純粋関数の参照)            (OK)
ドメイン → アプリケーション / UI / インフラ     (NG)
ドメイン → DOM・ブラウザAPI・Firebase         (NG)
UI / アプリケーション → firebase の import    (NG。Firebaseは、インフラ層だけが知る)
```

#### UI層(`src/ui`)
- **責務**: 18の画面と演出の描画、入力(ボタン、小人のタップ、言語の切り替え)の受付
- **許可される操作**: アプリケーション層の呼び出し、ドメイン層の型と純粋関数の参照(例: 小人の並べ方の計算)
- **禁止される操作**: ゲームの状態を直接書き換えること、Firebase を直接呼ぶこと

#### アプリケーション層(`src/app`)
- **責務**: `SessionController`・`RoundController`・`PressBatcher`・`AiHost`。画面の遷移、ドメイン層の呼び出し、`GameStore`(インターフェース)を通した読み書き、タイマー
- **許可される操作**: ドメイン層の呼び出し、`GameStore` と `GameView` のインターフェースを通した呼び出し
- **禁止される操作**: ルールの判定を自前で行うこと(判定は必ずドメイン層に任せる)

#### ドメイン層(`src/domain`)
- **責務**: `Schedule`・`Targets`・`Judge`・`Points`・`Ranking`・`Titles`・`Names`・`Rooms`・`AiBrain`(`src/domain/ai/`)・`Layout`(小人の並べ方とグラフの座標。`src/domain/layout/`)。機能設計書のアルゴリズムの実装
- **許可される操作**: 純粋な計算だけ
- **禁止される操作**: DOM・`window`・`document`・タイマー・`Math.random`・`Date.now` の直接使用(乱数と時刻は、引数で受け取る)
- ドメイン層は、ブラウザと Node.js の両方で動く。同じコードを、ユニットテスト、シミュレーション、ブラウザで使える

#### インフラ層(`src/infra`)
- **責務**: `GameStore` の実装(Firebase用と、テストや動作確認に使うメモリ上の実装の2つ)、`ServerClock`、`Prefs`、`TrafficMeter`(通信量の計測。テスト用)
- **許可される操作**: Firebase SDK の呼び出し、ブラウザの保存領域の利用
- **禁止される操作**: ルールの判定を行うこと

### 層のルールの強制

- ESLint の `no-restricted-imports` で、`src/domain` から、`src/app`・`src/ui`・`src/infra`・`firebase/*` への import を禁止する
- `src/ui` と `src/app` からの `firebase/*` の import を禁止する(Firebase を import してよいのは `src/infra/firebase/**` だけ)
- ESLint の `no-restricted-globals` で、`src/domain` での `window`・`document`・`setTimeout`・`requestAnimationFrame` の使用を禁止し、`no-restricted-properties` で `Math.random`・`Date.now` を禁止する

### GameStore を2つ用意する理由

`GameStore` は、インターフェース(機能設計書)として定義し、次の2つの実装を持つ。

| 実装 | 用途 |
|------|------|
| `FirebaseGameStore` | 本番と、Emulator Suite につないだ開発・テスト |
| `InMemoryGameStore` | ユニットテスト、シミュレーション(AIだけの回を、たくさん回す)、Firebase なしの画面の動作確認 |

これにより、ルールや AI の動きを、ネットワークなしで、速く、何度でも試せる。

## Firebase の構成

| 項目 | 設定 |
|------|------|
| プロジェクト | 1つ(本番)。開発とテストは、Emulator Suite を使うので、別のプロジェクトは作らない |
| データベース | Realtime Database。場所は、**シンガポール(`asia-southeast1`)**。日本からいちばん近い選択肢で、作成後は変更できない |
| 認証 | 匿名認証だけを有効にする。メールアドレスなどは、扱わない |
| 接続の設定 | `VITE_FIREBASE_API_KEY`・`VITE_FIREBASE_AUTH_DOMAIN`・`VITE_FIREBASE_DATABASE_URL`・`VITE_FIREBASE_PROJECT_ID`・`VITE_FIREBASE_APP_ID` を、環境変数(`.env.local`、Git管理外)で渡す。ひな形として、`.env.example` を用意する |
| エミュレータ | `VITE_USE_EMULATOR=true` のとき、認証(ポート9099)とデータベース(ポート9000)のエミュレータにつなぐ。Emulator Suite の画面は、ポート4000 |
| 作る作業 | プロジェクトの作成、データベースの場所の選択、匿名認証をオンにすること、セキュリティルールが意図どおりかの確認は、ユーザー(開発者)が自分で行う。手順は `docs/firebase-setup.md` に書く |

### 時計の同期

- `ServerClock` が、データベースの `.info/serverTimeOffset` を購読し、`now() = Date.now() + offset` を返す(端末の時計のずれを補正する)
- 時計から段階を計算する `Schedule` は、`now()` を引数で受け取る(ドメイン層は `Date.now` を使わない)
- 画面の切り替えのタイマーは、「次に切り替わる時刻 − `now()`」を計算して、`setTimeout` で待つ。待っている間に、`offset` が更新されたら、計算し直す

### 接続の検知

- `.info/connected` を購読して、オンライン・オフラインを判定する
- 起動時に、`initialConnectTimeoutMs`(5秒)つながらず、端末がオンライン(`navigator.onLine`)なら、混雑中の画面を出す。ゲーム中に切れたら、`offlineScreenDelayMs`(3秒)後に再接続の画面を出す(機能設計書の「接続の状態」)
- 切断時に自動で消す印(`presence`)は、`onDisconnect` で、あらかじめ登録する

### 匿名認証の保持

- 匿名認証の ID は、Firebase Auth が、ブラウザの保存領域に覚える(同じブラウザで開き直したときに、同じ人として扱うため)
- **itch.io の iframe の中では、保存領域が使えない環境がある**(特に Safari など、他のサイトの中に埋め込まれたページの保存を制限するブラウザ)。保存できない場合は、`inMemoryPersistence` に切り替えて、開いている間だけ、同じ人として扱う(開き直すと、別の人になる)。この場合は、自分の画面に、「このブラウザでは、記録を保存できません」と小さく知らせる(文言は、言語ごとの一覧に入れる)
- 実際にどのブラウザで保存できるかは、公開前に、実機で確認する(PRDの対応環境)

## データベースの配置とセキュリティルール

配置は、機能設計書の「データベースの配置」のとおり。ここでは、読み書きの権限(セキュリティルール)の方針と、書き方の雛形を定める。ルールは、`database.rules.json` に書き、Emulator Suite のテストで確かめる。

**ルールも、時計だけで段階を決める。** 回の開始・終了の時刻は、データベースに書かない。ルールの中で、サーバー時刻(`now`)から、画面と同じ計算(機能設計書の「1. 時計から段階を計算する」)をする。誰かが時刻を書き込む必要がないので、書く人がいなくて進行が止まることがない。

| ルールの中の式 | 意味(既定の設定値のとき) |
|------|------|
| `now % 360000` | いまの回の中の経過(`offset`)。1周 = `gatherMs + playMs + resultMs` = 360000 |
| `'' + (now - now % 360000) / 360000` | いまの回の `roundId`(`roundIndex` を10進の文字列にしたもの) |
| `now % 360000 >= 30000 && now % 360000 < 330000` | ゲーム中(`gatherMs` 〜 `gatherMs + playMs`) |
| `now % 360000 < 333000` | 終了の3秒後(`gatherMs + playMs + pointsGraceMs`)より前 |

- `$round` が、いまの回の `roundId` と一致しない書き込みは、拒否する(終わった回の数字やポイントを、あとから書き換えられないようにする)
- `pointsGraceMs` は、`resultMs` より短くする(猶予が、次の回にかからないようにする)
- **実装時に確かめること**: Realtime Database のルールで、数値と文字列を `+` でつなぐと、数値が10進の文字列になることを、Emulator Suite のテストで確かめる。できない場合は、`$round` の照合をやめ、時間の窓(上の表の3行目と4行目)だけで判定する。その場合、終わった回への書き込みを防げないが、最初の版は水増しを許容しているので、受け入れる(PRDの「セキュリティ」)

### 方針

| パス | 読む | 書く | 主な検証 |
|------|------|------|----------|
| `/users/$uid/profile` | ログイン済みなら誰でも | 本人だけ | 名前は1〜12文字(粗い検査。全角2・半角1の数え方は、クライアントで行う)、キャラクターの部品は、用意した種類の中から |
| `/users/$uid/stats` | ログイン済みなら誰でも | 本人だけ | 数字は、0以上の整数 |
| `/roomCount` | ログイン済みなら誰でも | ログイン済みなら誰でも | 1以上で、1回に1しか増えない |
| `/rooms/$room/memberCount` | ログイン済みなら誰でも | ログイン済みなら誰でも | 0〜20で、1回に1しか増減しない |
| `/rooms/$room/presence/$uid` | ログイン済みなら誰でも | 本人だけ | `joinedAt` は、サーバー時刻(`now`)と同じ |
| `/rooms/$room/aiHost` | ログイン済みなら誰でも | 空のとき、または、いまの担当が `presence` にいないとき、自分の `uid` を書ける | 書く値は、自分の `uid` |
| `/rooms/$room/rounds/$round` | — | AI担当は、`$round` がいまの回でないとき、まるごと削除できる(古い回の掃除) | — |
| `…/number` | ログイン済みなら誰でも | いまの回の、ゲーム中だけ | 数字は整数。1回の変化は、±50以内(`maxDeltaPerWrite`) |
| `…/players/$playerId` | ログイン済みなら誰でも | いまの回だけ。追加だけ(書き換え・削除は不可)。人間は、自分の `uid` の分だけ。AIは、AI担当だけ | `joinedAt` は `now`、種類と性格は、決めた中から |
| `…/pulses/$playerId` | ログイン済みなら誰でも | いまの回だけ。自分の分だけ(AIはAI担当) | `power` は 0〜3 |
| `…/points/$playerId` | 本人は、いつでも。他の人は、終了の3秒後から(終わった回は、いつでも) | いまの回の、ゲーム開始から終了の3秒後まで。自分の分だけ(AIはAI担当) | 0以上で、減らない |

- 「**3秒の猶予**」(`pointsGraceMs`): ゲーム終了の直前に押した分のポイントの書き込みが、遅れて届くことがあるため、ポイントは、終了から3秒間は、書き込める。その間は、他の人には読ませない(結果を見てから、書き換えられないようにするため)。そのため、**結果発表は、終了の3秒後**に出す(「終了!」「判定しています」の演出が、この間に当たる)
- 数字は、ゲーム終了より後は書けないので、最終値は、全員同じになる。終了の直前に押した分の一部は、サーバーに届かず、失われることがある(許容する)
- ルールの中の数値は、設定ファイル(`src/domain/config/defaultConfig.ts`)と同じ値にそろえる。ルールのファイルは、設定ファイルを読めないので、2か所に同じ値を書く。対応は次のとおり。値を変えるときは、両方を直し、`npm run test:rules` を通す

| ルールの中の値 | 設定値(`GameConfig`) |
|------|------|
| 360000(1周) | `gatherMs + playMs + resultMs` |
| 30000(ゲーム開始) | `gatherMs` |
| 330000(ゲーム終了) | `gatherMs + playMs` |
| 333000(ポイントの猶予の終わり) | `gatherMs + playMs + pointsGraceMs` |
| 20(1部屋の人数) | `roomCapacity` |
| 50(1回の変化の上限) | `maxDeltaPerWrite` |
| 12(名前の長さの粗い上限) | `nameMaxUnits` |

### ルールの雛形(抜粋)

実装時に、Emulator Suite のテストで、意図どおりに動くことを確かめて、完成させる。

```json
{
  "rules": {
    ".read": false,
    ".write": false,
    "users": {
      "$uid": {
        "profile": {
          ".read": "auth != null",
          ".write": "auth != null && auth.uid === $uid",
          ".validate": "newData.hasChildren(['name', 'character'])",
          "name": { ".validate": "newData.isString() && newData.val().length > 0 && newData.val().length <= 12" }
        },
        "stats": {
          ".read": "auth != null",
          ".write": "auth != null && auth.uid === $uid"
        }
      }
    },
    "rooms": {
      "$room": {
        "memberCount": {
          ".read": "auth != null",
          ".write": "auth != null",
          ".validate": "newData.isNumber() && newData.val() >= 0 && newData.val() <= 20 && (!data.exists() || (newData.val() <= data.val() + 1 && newData.val() >= data.val() - 1))"
        },
        "rounds": {
          "$round": {
            ".write": "auth != null && root.child('rooms/' + $room + '/aiHost').val() === auth.uid && !newData.exists() && $round !== '' + (now - now % 360000) / 360000",
            "number": {
              ".read": "auth != null",
              ".write": "auth != null && $round === '' + (now - now % 360000) / 360000 && now % 360000 >= 30000 && now % 360000 < 330000",
              ".validate": "newData.isNumber() && newData.val() - (data.exists() ? data.val() : 0) <= 50 && newData.val() - (data.exists() ? data.val() : 0) >= -50"
            },
            "points": {
              "$playerId": {
                ".read": "auth != null && ($playerId === auth.uid || $round !== '' + (now - now % 360000) / 360000 || now % 360000 >= 333000)",
                ".write": "auth != null && $playerId === auth.uid && $round === '' + (now - now % 360000) / 360000 && now % 360000 >= 30000 && now % 360000 < 333000",
                ".validate": "newData.isNumber() && newData.val() >= 0 && (!data.exists() || newData.val() >= data.val())"
              }
            }
          }
        }
      }
    }
  }
}
```

### ルールのテスト(`@firebase/rules-unit-testing`)

- 他人のポイントは、終了の3秒後まで読めず、その後は読める
- 終了の3秒後より後は、自分のポイントも書けない
- ゲーム中以外(集合中・終了後・結果発表中)は、数字の加算が拒否される
- いまの回ではない `$round`(終わった回、まだ来ていない回)への、数字・参加者・合図・ポイントの書き込みが拒否される
- ルールの中で、`'' + 数値` が10進の文字列になる(上の「実装時に確かめること」)
- AI担当は、終わった回を削除できる。いまの回は削除できない。AI担当でない人は、削除できない
- 1回に±50を超える数字の変化が拒否される
- 他人のプロフィール・実績・`players`・`pulses` が書けない
- `players` は、追加できるが、書き換え・削除できない
- 部屋の人数が、0〜20の外に出られない
- AI担当ではない人は、AIの `players`・`pulses`・`points` を書けない

## 通信量の見積もり

無料プラン(Spark)は、ダウンロード量が月10GBまで、同時接続が100まで(引き上げ不可)。通信量は、人数が増えるほど、急に増える(全員の操作が、全員に配信されるため)。

### 見積もりのモデル(概算。テストプレイで、測った値に置き換える)

- 1回の数字の更新(1人が押して、まとめて送る1回分)は、約80バイト。1回の合図は、約120バイト
- 1人あたり、数字の更新が1秒に平均1.2回(連打は0.2秒ごとにまとめる)、合図が1秒に平均0.6回(跳ねている人だけが送るので、全員は送らない)
- 1回の更新は、同じ部屋の、ほかの全員(人数−1)に配信される
- 1回のゲームは300秒

| 部屋の人数 | 数字の更新(配信/秒) | 合図(配信/秒) | 1秒あたり | 1ゲームあたり | 無料枠(月10GB)での目安 |
|-----------|------------------|-------------|----------|-------------|---------------------|
| 5人 | 24(約1.9KB) | 12(約1.4KB) | 約3KB | 約1MB | 約10,000ゲーム |
| 10人 | 108(約8.6KB) | 54(約6.5KB) | 約15KB | 約4.5MB | 約2,300ゲーム |
| 20人 | 456(約36.5KB) | 228(約27KB) | 約64KB | 約19MB | 約530ゲーム |

- 20人の部屋が、1時間(10ゲーム)続くと、約190MB。無料枠は、満員の部屋が、約53時間分
- 最初は、人数も少ない前提で、無料枠で足りる見込み。公開が広がったら、有料のBlaze(超えた分は、従量課金)に切り替える。料金は変わりうるので、切り替える前に、公式の料金表を確認する
- 実際の値は、下の「通信量の計測」で測る。この表は、測った値で作り直す

### 通信量の計測

PRDの機能9。数える仕組みは、機能設計書の `TrafficMeter`。ここでは、テストプレイでの測り方を定める。

- 本番のデータベースにつないで測る(Emulator Suite では、実際の通信量は測れない)
- `VITE_TRAFFIC_METER=1` を付けてビルドし、テスト用に配信する(itch.io の公開用のビルドには付けない)
- 人数を変えて(5人、10人、20人。人間が足りない分は、ブラウザのタブを増やす)、1回ずつ遊び、ゲーム終了の3秒後にコンソールに出る合計を記録する
- 同じ時間帯の、Firebase の管理画面の「ダウンロード量」も記録し、`TrafficMeter` の値との比(SDKやプロトコルの分の上乗せ)を求める
- 記録した値で、上の「見積もりのモデル」の表を作り直し、PRDのセカンダリーKPI「通信量」に、合格の目安を書く

### 通信量を抑える工夫

- **連打をまとめる**: 0.2秒ごとに、1回の加算にまとめる(「+1を5回」ではなく「+5を1回」)
- **数字と合図を、1回の送信にまとめる**: 複数の場所を、一度に書き換える命令(`update`)で、数字の加算と合図を、同じ送信に入れる。メッセージの数が減る
- **合図は、1人1秒に1回まで**: 跳ねているとき(直近で押したとき)だけ送る。押していない人は、送らない
- **ポイントは、他の人に配信されない**: 他の人は、終了の3秒後まで読めないので、購読しない。書き込みは、自分のぶんだけで、配信の量は増えない
- **購読の範囲を絞る**: いまの回の `number`・`players`・`pulses` だけを購読する。古い回は、購読せず、AI担当が削除する(残すのは、`roundsToKeep` = 2回分)
- さらに必要なら: 合図の間隔を長くする(例: 2秒)、合図の `power` を段階(0〜3)にまとめて、変化が少ないときは、送らない

### 同時接続

- 1つのブラウザの画面(タブ)が、1接続を使う。見ているだけの人、待機中の人も数える
- 無料プランでは、100接続を超えた人は、つながらない(機能設計書の「混雑中」の画面)。当面は、これで足りる。届きそうになったら、Blazeへの切り替え(上限が大きく上がる)を検討する。サーバー自体の入れ替えは、それでも足りなくなってからの話

## 画面のレイアウト

- 基準は、幅390pxの縦画面。幅360px以上で、横スクロールなしで、すべての画面が収まる
- PCや、幅の広い画面では、画面全体を、幅390pxの縦長のまま、中央に置く(横幅は広げない)
- `viewport` を設定し(`width=device-width, initial-scale=1`)、ブラウザの標準のピンチズームは、止めない(読みにくい人のため)
- 画面の上の余白(約20px)に、言語の切り替えボタンを置く(幅・高さとも、グラフや小人を隠さない小ささ)
- 画面の見本は、`docs/design/screens/` を正とする

## 動き(アニメーション)の実装方針

- 跳ねる、降りてくる、きらめく、点滅する、浮かぶ、弾む、脈打つ動きは、すべて **CSSのキーフレームアニメーション**(`transform`・`opacity`)で作る。JavaScriptは、クラスの付け外しと、アニメーションの長さ・高さ(CSS変数)の設定だけを行い、毎フレームの更新はしない
- 小人の跳ねる高さと速さは、最新の合図の `power` から計算し、CSS変数(`--h`、`animation-duration`)で渡す
- グラフは、SVGの `polyline` の点を更新する。数字が届くたびに、全体を描き直さず、一定の間隔(例: 100ms)ごとに、まとめて描く
- 端末の「動きを減らす」設定(`prefers-reduced-motion`)が有効なときは、CSSの `@media (prefers-reduced-motion: reduce)` で、動きをやめる。画面の見本のCSSに、その書き方が入っている

## 言語(i18n)の実装

- すべての文言は、言語ごとの一覧(`src/app/i18n/messages.ja.ts`・`src/app/i18n/messages.en.ts`)に置く。キーは、型で管理し、日本語と英語の両方にないキーは、ビルドで失敗させる
- 一覧には、画面の文言、称号、AIの名前、演出の文字、メッセージ、注意書きを入れる。他の人が付けた名前は、翻訳しない
- 英語の文言は、日本語の文言をもとに、Claude Code が作る。短く、やさしい言葉にする。日本語より長くなるので、画面の部品は、文字の長さに合わせて広がるか、折り返す
- 書体は、`Dela Gothic One` と `M PLUS Rounded 1c`。どちらも、英数字を含む
- 選んだ言語は、ブラウザに覚える(`Prefs`)。覚えられない環境では、開いている間だけ保つ。初めて開いたときは、ブラウザの言語設定(`navigator.language`)に合わせる(日本語なら日本語、それ以外は英語。仮)

## セキュリティアーキテクチャ

### データ保護

- **個人情報**: 収集しない。名前は、本人が付けたニックネームだけ。メールアドレスなどは、扱わない(匿名認証)
- **アクセス制御**: データベースのセキュリティルールで行う(上の表)。自分のIDのデータだけ書ける。他人のポイントは、終了の3秒後まで読めない。終了後の数字の加算はできない
- **機密情報管理**: Firebase のAPIキーは、公開される前提で、機密として扱わない。サービスアカウントの鍵など、本当の秘密情報は、リポジトリにも配信物にも置かない。butler を使う場合のAPIキーは、CI の秘密情報に置く

### 不正への備え

- 最初の版は、成功回数やポイントを、ブラウザから書き込む。詳しい人は、自分の実績を水増しできる(PRDで許容)
- **最初の版から入れる**: セキュリティルールで、1回の数字の変化(±50)、ポイントが減らないこと、終了後の書き込みの拒否を行い、乱暴な不正は、防ぐ(ルールを書くだけで済み、サーバー側のプログラムはいらない。終了後の書き込みの拒否は、最終値を全員同じにするためにも、必ず必要)
- **あとで(P2)**: 公開が広がり、ランキングを競うようになったら、サーバー側の関数(Cloud Functions)で、判定と加算を行う。また、Firebase の App Check(正規のアプリからのアクセスかを確かめる仕組み)を検討する

### 入力検証

- **名前**: 保存の前に、`validateName` で、長さ(全角6文字・半角12文字まで)と使える文字を検証する。ルール側でも、粗い検査(12文字以下)を行う
- **キャラクター**: 用意した種類の中からだけ選べる。ルール側でも、決めた値だけを許す
- **文字列の表示**: 他の人が付けた名前は、HTMLとして解釈せず、必ず文字として表示する(`textContent` を使い、`innerHTML` にユーザー由来の文字列を渡さない)
- **データベースから読んだ値**: 形が想定と違うときは、無視するか、既定の値にする(壊れたデータで、画面が止まらないようにする)

## スケーラビリティ設計

### データ増加への対応

- **想定データ量**: 1部屋20人まで。1回あたり、`players` が最大20件、`pulses` が最大20件、`points` が最大20件、`number` が1件。古い回は削除し、1部屋に残るのは2回分(`roundsToKeep`)なので、データは増え続けない。AI担当がいない間(部屋に人間がいない間)は削除が止まるが、その間は、新しい回のデータも増えない
- ユーザー数が増えると、`/users` が増える。1人あたり、数百バイトなので、当面は問題にならない

### 機能拡張性

| 将来の機能(PRD) | 今の設計での備え |
|------|------|
| イベント用の大画面モード(19) | 画面(UI層)が見るのは、ドメイン層が組み立てた `RoundView` だけ。表示専用の画面を、同じ `RoundView` から、別に作れる。URLで、部屋を指定して開く形を想定する |
| 専用コントローラーと大画面(20) | 操作は、「どの席が、+1か−1か、何回分か」という、小さな形で、データベースに書く(`PressBatcher` の入力)。画面のボタンも、将来のコントローラーも、同じ形で書く。ルール(判定・ポイント・進行)は、画面から切り離してあり、そのまま使える。席(プレイヤー枠)は、匿名のID(`uid`)とは別の項目として、`Player.id` で持つ。今は、人間の `Player.id` に `uid` をそのまま使っている。1つの端末で複数の席を持つときは、`id` の作り方だけを変える |
| 部屋の均等な分け直し | 部屋の割り振りは、`Rooms` という純粋な関数に閉じ込めてある。集合のときに、分け直す関数を足せる |
| 20人そろったら早く始める | 進行は、時計だけで決めている。早く始めるには、誰かが「早く始めた」と書く仕組みが要る。条件付きの書き込みで、1人だけが書けるようにする |
| ランキング(15) | `/users/$uid/stats` を、並べ替えて表示する。人数が増えたら、集計用のデータを別に持つ |
| 不正対策(17) | 判定と加算を、サーバー側の関数に移す。ドメイン層の純粋な関数(`judge`・`settle` など)を、そのまま使える |
| 言語の追加 | 言語ごとの文言の一覧を、1つ足せばよい |

- **対象**: 上の「ルールのテスト」の項目

### 結合テスト(Firebase Emulator Suite)
- **フレームワーク**: Vitest(Node.js から、複数の Firebase アプリを同時に動かす)。`firebase emulators:exec` で、エミュレータを起動してから実行する
- **対象**: 機能設計書の「Firebase Emulator Suiteでのテスト」(同時に押しても取りこぼさない、部屋の割り振りの競争、AI担当の決まり方と引き継ぎ、接続の切断と再接続)

### シミュレーション
- **フレームワーク**: Vitest(通常のテストとは別のコマンド `npm run test:sim` で実行する。時間がかかるため)
- **対象**: AIだけの回を、人数(5、10、20)と性格の組み合わせを変えて、たくさん回し、成功率・ぴったり率・ポイントの分布を調べる。`InMemoryGameStore` と、時刻を進められる模擬の時計を使うので、速く回せる。乱数は、種(シード)を固定できる疑似乱数を使い、再現できるようにする
- **実行のタイミング**: AIの動きや、目標・範囲・倍増タイムを変えたとき、および公開前

### E2Eテスト
- **ツール**: Playwright(Chromium・Firefox・WebKit。PRDの対応環境の、PCの Chrome / Edge は Chromium、Firefox は Firefox、Safari と iOS Safari は WebKit で確かめる)
- **対象**: ビルドした `dist/` を、静的サーバーで配信し、Emulator Suite につないで動かす。複数のブラウザコンテキストで、複数人の参加を再現する
- **シナリオ**: 機能設計書の「E2Eテスト」(初回の登録から、結果発表、次の集合中まで。途中参加、満員の待機、終了間際の待機、結果発表中の待機、通信が切れて戻る、スマホ幅360pxでの表示、日本語と英語、「動きを減らす」)。スマホ幅では、タッチ操作(`hasTouch`)を有効にする
- **時計**: テスト用に、時計のずれ(`offset`)を差し替えて、「集合中」「ゲーム終了の直前」などの時刻に、すぐ進められるようにする(本番の画面には、この指定の手段を出さない)

## 技術的制約

### 環境要件
- **遊ぶ環境**: PRDの対応環境のブラウザ。JavaScript が有効で、インターネットにつながっていること
- **画面**: 幅360px以上
- **開発環境**: devcontainer(Node.js LTS、Java 21、GitHub CLI)。Playwright のブラウザと、Firebase CLI は、devcontainer 内にインストールする

### パフォーマンス制約
- 実行時の外部通信は、Firebase と、書体の読み込みだけ
- 連打のまとめ送りと、合図の間引きを、必ず行う(通信量のため)

### セキュリティ制約
- トラッキングなどの外部スクリプトを使わない
- 本当の秘密情報(サービスアカウントの鍵など)を、リポジトリと配信物に含めない
- ユーザー由来の文字列を、`innerHTML` に渡さない

## 依存関係管理

| ライブラリ | 用途 | 区分 | バージョン管理方針 |
|-----------|------|------|-------------------|
| firebase | 匿名認証・Realtime Database | 実行時(`dependencies`) | 12.x系の、実装時点の最新の安定版に固定。メジャーの更新は、動作確認をしてから |
| typescript | 型チェック・コンパイル | 開発時 | `~5.9.0`(パッチのみ自動)。メジャーの更新は typescript-eslint の対応を待つ |
| vite | 開発サーバー・ビルド | 開発時 | `^8.x`(マイナーまで自動) |
| vitest / @vitest/coverage-v8 / @vitest/ui | テスト | 開発時 | `^5.x`。3つのバージョンをそろえる |
| @types/node | Node.js の型 | 開発時 | `^24.x`。Node.js のメジャーバージョンに合わせる |
| @playwright/test | E2Eテスト | 開発時 | `^1.63.x` |
| firebase-tools | Emulator Suite・ルールの反映 | 開発時 | 最新の安定版(8.14.0 以上) |
| @firebase/rules-unit-testing | ルールのテスト | 開発時 | `^5.0.2`。`firebase` のメジャーバージョンに合わせる(firebase を 13 に上げるときに、6.x に上げる) |
| tsx | スクリプトの実行 | 開発時 | `^` の最新安定版 |
| eslint / typescript-eslint / prettier / husky / lint-staged | 静的解析・整形・コミット前チェック | 開発時 | 既存の指定を維持 |

- バージョンの指定の違い: 実行時に読み込む `firebase` は、配信物の中身と通信の動きが変わるので、厳密に固定する。開発時の道具は、マイナーの更新を自動で受け入れる(`^`)。`typescript` は、マイナーの更新で型チェックの結果が変わることがあるので、パッチだけ(`~`)にする
- 実行時の依存は、`firebase` だけにする。ほかに増やす場合は、理由を、このドキュメントに書く
- `package-lock.json` をコミットし、全員が同じバージョンを使う
